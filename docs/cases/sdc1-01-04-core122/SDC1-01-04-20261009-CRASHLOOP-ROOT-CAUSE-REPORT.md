## 执行摘要

10 月 9 日，01-04 单板在 11:19 至 23:47 之间发生 26 次异常复位（当日 SEL 共 43 次 boot 事件，另 17 次为运维人员手动上下电，不计入），午后一段呈 17 分 12 秒 ±1 秒的定时器级精确周期。全天 BMC 传感器无任何电压、温度、电源异常。

根因【实锤】：**物理核 MPIDR `0x0900060200`（逻辑 CPU122）的核内缺陷**——即 9 月报告定性的"水银核心"。10 月 2 日机架级断电抹掉了固件的摘核状态，坏核回到启动集合。本次经 BMC 控制台黑匣子捕获 5 次内核崩溃，全部首错于该核；对两个内核版本的反汇编将故障定位到具体指令与寄存器，证明该核的访存通路会**把"地址→数据"的对应关系弄错**：装载返回别的地址的合法内容（四个被调方保存寄存器被替换为无关内核指针、只读数据段的字符串常量进入寄存器、返回地址被换成 0 导致跳转失败），并对**必然已映射的地址**报出"页表项为零"的翻译故障。

复位循环的最后一环【实锤】：内核崩溃后挂死，SBSA 通用看门狗（固件级，约 900 秒）超时后热复位整机——固件日志原文 `SBSA watchdog timeout, hot reset system`。周期 = POST 115s + 内核存活约 30s + 看门狗 885s ≈ 1032s = 17′12″。

微架构定位【强推】：故障域收窄至该核**私有访存通路的选择/关联逻辑**（不是存储单元，不是共享层）。被交换的都是完整合法数据，ECC 全程无感——存储单元故障物理上造不出"别的行的完整数据"（§5.2 论证）；同簇的 CPU123 两度证明健康，排除一切共享结构（§5.1）。候选位点排序：**私有 L2 的 MSHR 响应关联（单点可解释全部观测）＞ L1D way 选择 + 页表遍历读通路（双点）**；二者之别有待下次 vmcore 或微分实验判定（§5.4）。

当前状态：CPU122 已离线，127 核稳定运行。三项行动：① 持久化核隔离（开机自动 offline）；② 修复 kdump 与看门狗的冲突（本次转储被看门狗中止，"读侧误读 vs 写侧清零"的判据因此缺失）；③ 该 die 送厂失效分析（检查清单见 §8.3）。

## §1 现象与数据基线

### 1.1 复位的时间结构

26 次异常复位呈三种时间形态：

| 形态 | 时段 | 次数 | 间隔特征 |
|---|---|---|---|
| 晨间簇 | 11:19–11:49 | 6 | 48s–17min；最短 48s 短于一次 POST（约 115s），说明部分复位发生在固件阶段 |

## §3 失效定位到核：CPU122

### 3.1 证据来源

BMC 芯片内有一个"黑匣子"：它持续把主机控制台上内核打印的每一行收进一个 2MB 环形缓冲（`ipmcget -d systemcom` 取回，E-4/E-5）。内核崩溃时会打印完整的出错报告——出错指令、出错地址、出错原因码、全部 31 个通用寄存器。本次取回的缓冲覆盖 10-09 晚间以来的 5 次完整崩溃。

配套手段是反汇编：从 0104 主机 `/boot` 取回两版内核镜像与符号表（E-6/E-7），可把报告中每一条"出错指令"逐条还原成汇编原文。

### 3.2 死亡故事：CPU122 的最后 27 秒

以第 5 次崩溃为例，完整走一遍——这一个故事里包含本案全部三类证据。

23:34:44，运维人员把 CPU122 重新上线——当晚唯一一次人为干预，此前这台 122 核的系统已安静运行 80 分钟。

上线后 17 毫秒，内核在该核自己的热插拔线程里打印了一条警告——为这个核重建调度结构时发现内部数据不一致：

```
[4784.336] CPU122: Booted secondary processor 0x0900060200   ← 该核进入内核
[4784.357] WARNING: CPU: 122  Comm: cpuhp/122  at kernel/sched/topology.c:1021
```

接下来的 27 秒，这个核没有分到任何任务，一直空闲。23:35:11，一个中断到来。它应答中断、交给内核分发、再查询下一个——中断控制器返回了特殊号码 1021（"没有更多待处理的中断"），于是收尾返回。收尾的第一条指令，是从栈上取回本轮中断处理开始时保存的两个寄存器值。硬件在这一步报告：**这个地址不存在**：

```
[4811.420] Unable to handle kernel paging request at virtual address ffff8000803d4010
           ESR = 0x96000007   FSC = 0x07: level 3 translation fault   ← "地址无映射"异常
CPU: 122 PID: 0 Comm: swapper/122        ← swapper/122：该核的空闲任务
pc : gic_handle_irq+0x74    sp : ffff8000803d4000
```

内核随即崩溃，打印出全部 31 个寄存器。其中 4 个寄存器的值，按程序逻辑不可能出现（§4.1 逐步证明）。12 分钟后，SBSA 看门狗把整台机器热复位——这就是 23:47:19 那次异常复位。

这个故事给出三类证据：**上线 17ms 的调度器警告**（该核刚参与运行，处理它的数据就出了不一致）；**读"肯定存在的地址"报不存在**（那两个寄存器是同一轮中断处理刚开始时保存的，保存没有报错）；**四个"不可能"的寄存器值**。§4 将证明它们为什么指向同一种缺陷。

### 3.3 从一次到五次

黑匣子共捕获 5 次崩溃，死法各异，共性惊人：

| # | 内核 | 死法（按 §4.0 概念解读） | 上线→出事 |
|---|---|---|---|
| 1 | 旧 .3.154 | 函数返回前核对栈上的防篡改密钥，发现密钥被换过（`vsnprintf` 金丝雀） | 9.9ms |
| 2 | 新 .4.13.167 | 返回地址寄存器变成 0，CPU 跳到地址 0 取指令，报"地址 0 无映射" | 33.7ms |
| 3 | 新 .4.13.167 | 读一个任务结构体的字段，报"该地址无映射"（`__switch_to`） | 18.0ms |
| 4 | 旧 .3.154 | 同 #3，且是**同一行代码**（两版内核此函数相同） | 18.8ms |
| 5 | 新 .4.13.167 | §3.2 的故事：中断收尾读保存的寄存器，报"无映射" | 27.08s |

前四次发生在系统启动风暴中：用户态在开机约 35 秒处把启动参数限制之外的 CPU 全部热插拔上线，CPU122 上线后 10–34 毫秒内出事。三条横向共性：

F1 **五次的首错核全部是 CPU122**——出错报告里 `CPU: 122`，无一例外；
F2 #2/#3/#4 的寄存器转储中出现**同一组只读数据段常量**（SWAR 常量，§4.0/§4.1 详解）；
F3 五次的直接死因全部是"读"（装载、密钥核对）或"读到的值所驱动的跳转"——没有一次是写指令当场出错。

### 3.4 统计定位与反证

**正面：首错核的集中度。** 10 月 5/5 首错于 CPU122；9 月（前置报告）5/5 于同一物理核。合计 10 次近似独立事件，10 次全中同一核。如果病灶是所有核共享的东西（内存、互连、系统软件），受害者应当随机散布在 126 个核里——10 连中同一核的概率为 128 × (1/128)¹⁰ < **10⁻¹⁸**；即便只计 10 月的 5 次也是 (1/128)⁴ ≈ 3.7×10⁻⁹。只有"病灶在这个核自己内部"才能产生这种集中。

**反面：摘掉它就健康。** 与坏核**同簇**的 CPU123（共享同一块 L3 和簇内互连）两度证明健康：9 月坏核被固件摘除后，CPU123 顶替其编号干净启动；10 月至今它一直在线，与其余 126 核共同稳定运行。凡是簇一级及以外共享的东西它俩都在用——它没病，病就不在共享层。

**必要条件。** 五次崩溃全部满足"CPU122 在线"；该核不上线的启动分别存活 5 天与 11 小时以上。该核参与运行是死亡的必要条件，且**无需用户负载**——第 5 次崩溃前它纯空闲 27 秒，一轮中断处理即致命。

> **本节结论【实锤】**：失效主体 = 物理核 `0x0900060200` 的核内私有域。它做错了什么——§4；错在核内哪一段——§5。

## §4 缺陷行为模型：这个核在做错什么

### 4.0 前置概念（读懂本章所需）

- **寄存器与被调方保存寄存器**：CPU 有 31 个通用寄存器，存放正在使用的数据。调用约定（AAPCS）规定其中 x19–x28 与 x29 由被调函数负责保护：被调函数进入时把自己的值存到栈上，返回前原样取回。x29 是帧指针——函数进入时被设为自己的栈帧起点，此后调用链上无人再改动它。
- **栈帧**：每次函数调用在栈上占一块内存，存放局部变量和保存的寄存器；函数返回即归还。崩溃 #5 死在"从栈帧取回寄存器"这一步。
- **金丝雀（stack canary）**：编译器在每个函数栈帧里放一个随机密钥，函数返回前核对；栈内容被意外改写则核对失败、内核主动崩溃。这是崩溃 #1 的死法。
- **虚拟地址、页表、PTE、TLB、页表遍历**：内核用虚拟地址访问内存；每个虚拟页在页表里有一条映射记录（PTE，页表项），写明它对应哪个物理页。CPU 内有一张快速缓存（TLB）记住最近查过的条目；TLB 没命中时，由专门硬件（页表遍历器，PTW）逐级去读页表。读到的 PTE 为 0，即"这个地址没有映射"，访问立即触发异常——崩溃 #3/#4/#5 报的就是它。
- **SWAR 常量**：内核里优化过的字符串函数（strlen/strcmp）一次处理 8 个字节，用一组固定掩码常数（`0101010101010101`、`7f7f7f7f7f7f7f7f`、`fefefefefefefeff`、`8080808080808080`）检测字节状态。它们存放在内核**只读数据段**，只会被读取——正常情况下永远不该出现在保存-恢复的寄存器里。

### 4.1 现象一：寄存器里装着不属于它的数据

以崩溃 #5 的四个寄存器为对象，六步推导：

1. **先证明"内容错了"。** 崩溃转储里 x29 = `ffff80008111bc00`。但反汇编（E-6）显示：`gic_handle_irq` 进入时执行 `mov x29, sp`（x29 := 本函数栈帧起点 `0xffff8000803d4000`）；此后整个函数没有再写 x29；它调用的函数按调用约定必须原样恢复 x29。因此出错那一刻 x29 必然仍等于 `0xffff8000803d4000`。实测值与应有值相差约 13 MB，指向另一个内存对象——它不可能被"执行"出来，只能是内容本身错了。
2. **错成什么样？** x29 的错误值是一个 16 字节对齐的合法内核地址（落在空闲任务的栈区）；x19/x20/x21 的错误值同样是真实存在的内核地址——另外的任务栈、设备寄存器映射区。它们不是乱码：每一个都是这台机器上**真实数据对象的地址**。
3. **排除位翻转。** 存储单元（寄存器堆/缓存的位单元）损坏的表现是某一位粘在 0 或 1：错误值应呈现固定的位模式，且与"当时机器上有什么"无关。观测到的却是另一个对象的**完整、完好的地址**。位单元故障造不出别的对象的地址。
4. **排除计算错误。** 寄存器取值只有两条来源：执行单元算出来，或者一次装载把内存数据写回。这四个无关指针不可能由当时的计算产生（该函数在处理中断应答，算的是中断号和掩码）——所以它们是某次**装载**写进来的。
5. **结论。** 那次装载访问的地址是 A（栈上的保存槽），写回寄存器的却是地址 B 的内容——**读 A，拿回 B 的数据**。称之为**错行装载**：访存通路把"哪个地址对应哪些数据"弄错了。
6. **三个独立佐证。**
   a. **SWAR 常量（F2）**：只读段的掩码常数出现在 #2/#3/#4 的寄存器里——它们进入寄存器的唯一途径是被装载；出现即错行装载，来源是当时流经同一通路的其他读请求。三个不同崩溃、两个内核版本。
   b. **崩溃 #2**：某次装载把 0 写进了返回地址寄存器 x30，函数返回时 CPU 跳到地址 0 取指令，报"地址 0 无映射"（ESR=0x86000004，取指中止）。0 同样是合法数据——零填充页的内容。
   c. **崩溃 #1**：金丝雀核对失败——写入的密钥与读回的不一致，写与读至少一侧被换。

### 4.2 现象二：读"肯定存在"的内存，硬件却说"不存在"

1. **事实。** 崩溃 #5 的出错指令是从栈帧取回 x19/x20（`ldp x19, x20, [sp, #16]`）。要读的槽位，是**同一轮中断处理开始时**同一函数的第一条保存指令写的——写的时候没有报任何错误。对未映射地址的写会立刻触发异常；没报错，说明写入那一刻这个页的映射是好的。
2. **矛盾。** 读的时候，页表遍历器读出的 PTE 是 0（页表上层各级表项都有效，唯独最末一级为零）——"这个地址没有映射"。
3. **同两次崩溃同型。** #3/#4 读的是一个**正在参与调度的任务**的结构体字段（`x19+0x13c8` 与出错地址逐位吻合，E-7）——那个对象每毫秒都被调度器读写，映射不可能不存在——同样报 PTE=0。
4. **两种解释，同一处错。**
   - 解释 A：PTE 在内存里**真的是 0**——某次写入把 0 落到了这个页表项上，即**写入落到了错误的行**（错行写入），受害对象是页表。
   - 解释 B：PTE 在内存里是好的，**页表遍历器读错了**——遍历器的读请求不查 L1 缓存、直接走这个核的私有 L2（§5.0），错行装载发生在这条通路上。
   两个解释错的是同一个东西——地址与数据的对应关系；A 是写侧，B 是读侧。

### 4.3 两侧同一缺陷：证据闭环

1. **写侧有 9 月的直接观测。** 前置报告记录：页表页被清零、被内核代码字节覆写，且**跨核可见**——其他核遍历页表也看到坏表。内存确实被写错过，不是这个核的错觉。
2. **为什么 10 月只见读侧（F3 的解释）。** 错行写入是静默的：写指令本身不报错，被写坏的行要到稍后、被别人读时才出事，且出事位置远离写入处。装载出错则当场可见。10 月五次全部当场死于"读"，与这一不对称完全自洽。
3. **ECC 为什么全程无感。** ECC 校验的是"一个字里的位有没有翻转"。错行交换的是**两份都完好的合法数据**——送来的码字本身没有任何位错，校验必然通过。这解释了两个月零 CE/UE，也直接给出 §5.2 的结论：缺陷不在带校验的存储单元里。

### 4.4 故障模型与触发画像

> **故障模型【强推】**：CPU122 的私有访存通路以低概率把"地址→数据"的对应关系弄错——装载返回别的行的内容，写入落到别的行，页表遍历读出错误条目。被交换的双方都是合法数据，ECC 与 RAS 全程不可见。

**触发画像**：五次出事全部处于访存密集窗口——#1–#4 在启动风暴（模块映像拷贝、逐核上线回调），#5 在嵌套中断的深调用树。#5 之前该核纯空闲 27 秒、无任何任务调度，一轮中断处理即致命：**缺陷不需要用户负载，正常内核活动的访存密度已足够**。

## §5 微架构定位：缺陷在核内的哪里

### 5.0 前置概念（缓存与访存通路的组织）

- **缓存层次**：每个核有私有的 L1（几十 KB）与 L2（几百 KB）；每簇几个核共享 L3；再往外是内存。每次访存先查 L1，查不到（未命中）逐级向下，数据再逐级送回。
- **组相联与 tag/way**：缓存分成许多组，每个地址按其地址位映射到固定的一组；组里有 N 行（N 路）。查找时并行比较每行的标签（tag），命中的那一行（way）的数据被取出送回。**比较或选择出错，会送回同组另一行的数据——内容完好，但属于别的地址。**
- **MSHR**：未命中时，核向下一级发出读请求，在途请求登记在 MSHR 队列里；数据返回时按登记把数据交给对应的请求。**关联出错，则 A 的请求拿到 B 的数据。**
- **页表遍历器的读**：不查 L1、不查 store buffer，直达本核私有 L2。
- **store buffer 与转发 CAM**：写先进入 store buffer 排队提交；紧随其后的读若命中同一地址，由按地址并行匹配的 CAM 直接转发未提交的数据。
- **旁路网络**：执行结果不经寄存器堆、直接送给等待它的下一条指令的数据线。

搜索空间（缺陷只可能在下列结构中）：

```
CPU122 核内私有                         簇内共享          整机共享
─────────────────────────────          ────────         ────────
执行单元 → 旁路网络 → 寄存器堆
装载/存储队列 LSU（store buffer、转发 CAM）
L1（tag 阵列 / way 选择 / 数据阵列）      L3/HHA  ←——→    互连  ←——→  内存
MMU（TLB / 页表遍历器 PTW）
私有 L2（tag / 数据 / MSHR 在途跟踪）
```

以下三层逐层收窄：先排除共享层，再排除存储单元，最后在选择逻辑内部排序。

### 5.1 第一层：私有结构，不是共享结构

1. **共享层无法产生单核集中。** L3、互连、内存里的数据，任何核都会读。若坏数据产生在共享层，受害核应随访问分布随机散布在 126 个核中——不可能 10 次崩溃全部首发于同一核（§3.4，<10⁻¹⁸）。
2. **同簇对照排除簇级共享。** CPU123 与坏核共享同一块 L3 和簇内互连——簇一级共享的东西它俩都在用。它两度健康（9 月顶替启动、10 月在线至今），簇级共享结构随之排除。
3. **结论**：缺陷在 CPU122 独有的五类结构中——旁路网络、LSU（含 store buffer 与转发 CAM）、L1、TLB/页表遍历器、私有 L2。

### 5.2 第二层：选择逻辑，不是存储单元

1. **存储单元坏掉的物理表现。** 每个存储单元（寄存器堆位单元、缓存数据阵列的单元、内存芯片单元）存放的是**某一行数据的某一个位**。它损坏，只能把自己那一位固定为 0 或 1——把本行的数据改坏；它没有任何途径引入别的行的内容。要让"另一个地址的完整 64 字节"出现在这里，需要 512 个位同时精确变成另一行的值——存储单元故障不具备这种因果能力。
2. **观测到的恰是另一种东西。** §4.1 已证：错误值是别的对象的完整、完好数据。这只有"决定取哪一行 / 数据属于哪个请求"的逻辑出错才能产生。
3. **辅证。** 数据阵列带 ECC/奇偶校验，位单元故障会被检出并计数——两个月零 CE/UE。
4. **结论**：缺陷在选择/关联逻辑中——tag 比较、way 选择、转发 CAM 匹配、MSHR 响应关联、TLB 查找。

### 5.3 第三层：哪一段选择逻辑

先列出各访问路径经过的选择点：

| 访问路径 | 经过什么选择逻辑 |
|---|---|
| L1 命中的装载 | tag 比较 → way 选择（从同组多行中选出命中行的数据） |
| store buffer 转发 | 地址 CAM 匹配 |
| L1 未命中的装载 | MSHR 把下一级返回的数据关联回正确的在途请求 |
| 页表遍行器的读 | 不经 L1、不经转发，直达私有 L2（同属请求-响应关联） |
| 写提交 / L1 写回 | L1 分配与 L2 写路径的命中匹配 |

逐项排除（每个假说 → 它解释不了的具体观测 → 排除）：

- **"只有转发 CAM 坏"**：转发只能送出 store buffer 里排队的数据。SWAR 常量在只读段、从未被写过——不可能是任何 store 的数据，解释不了它们进寄存器；页表遍行器也不查 store buffer，解释不了 PTE=0。→ 排除为主因。
- **"只有旁路网络坏"**：旁路只能送本核指令刚算出的结果——同样给不出只读段常量，也给不出 PTE=0。→ 排除为主因。
- **"只有 L1 的 tag/way 选择坏"**：解释不了 PTE=0——页表遍行根本不查 L1；除非再假设遍行器一侧另有独立缺陷（两个缺陷，见下）。→ 单独不成立。

**收敛。** 剩下唯一能以**一处故障**同时覆盖错行装载、遍行误读、错行写入的，是**私有 L2 的 MSHR/响应关联**：未命中的读、遍行器的读、写回，全部流经 L2 的请求-响应结构；一处"把返回数据关联回错误请求"的缺陷即可产生全部三类表现。

**该假说的前提，与诚实声明。** 它要求 §4.1 的错行装载都发生在"L1 未命中"的读上（命中 L1 的读不经过 L2）。这些读访问的是深调用树之后被挤出缓存的栈保存槽——前提成立合理；但崩溃报告不含命中/未命中信息，**现有数据无法证明这一前提**。若前提不成立（某次出错的是 L1 命中读），最小修改是"L1 way 选择 + 遍行器读通路"两处缺陷。

> **位点排序【假设级】**：① 私有 L2 的 MSHR/响应关联——单点覆盖全部三类观测，代价是上述不可证前提；② L1 way 选择 + 页表遍行读通路——覆盖全部（含命中类错行装载），代价是需两个独立缺陷；③ 转发 CAM / 旁路网络——仅解释子集，已排除为主因，降为并存可能。

### 5.4 判别途径

1. **vmcore 页表真值（决定性）**：下次崩溃拿到完整内存转储后，直接读故障地址的 PTE——内存中有效 → 解释 B（读侧）；真的是 0 → 解释 A（写侧）。前提是先解决 kdump 与 SBSA 看门狗的冲突（§8.4）。
2. **微分实验（送修前若需位点结论）**：在 CPU122 上跑两个循环读已知模式——一个 4KB 缓冲（恒 L1 命中）、一个 1MB 缓冲（恒未命中、走 L2）。只有未命中侧出错 → ①；两侧都错 → ②。
3. 触发画像（§4.4：五次全在高未命中密度窗口）为 ① 提供方向性支持。

### 5.5 与 9 月报告的衔接

9 月定性为"核内装入返回/存储提交通路的行标识故障（D1/D2 错源/错行替换族）"。本案确认并细化：新增寄存器级直接观测（9 月仅经崩溃转储间接推断）、页表遍行器读通路这一观测面、跨内核同指令位点复现、以及"无需用户负载"的触发下界。

> **本节结论【强推】**：故障域 = 核私有访存通路的选择/关联逻辑；位点排序 ① L2 MSHR ＞ ② L1 way + PTW。未决：①/② 之别（§5.4）。

## §6 复位动力学：为什么循环、为什么 17′12″

### 6.1 传播链【实锤】

```
CPU122 参与运行（在启动集合内 / 被热插拔上线）
  → 访存缺陷激发（§4 任一表现）→ 内核 panic
  → panic 路径挂死（panic=30 的重启未触发：任务栈转储阶段死锁；早期启动时 kdump 未就绪）
  → SBSA 通用看门狗超时 → 固件热复位整机
  → POST → 内核启动 → CPU122 再上线 → 再 panic → 循环
```

看门狗环节为固件日志直接证据（黑匣子原文）：`NOTICE: SBSA watchdog timeout, hot reset system`。

### 6.2 周期算术

午后循环实测 1031–1033s，分解：POST 115s（22:13:00→22:14:55，操作日志实测）+ 内核存活至 panic 约 30s（自启动起；自该核上线起为 10–34ms，见 §3.3）+ 看门狗约 885s ≈ **1032s = 17′12″**。三个分量中只有看门狗是大量级常数——周期性由此而来。

### 6.3 定向复现全链（10-09 22:13–23:47）

| 时刻 | 事件 | 证据 |
|---|---|---|
| 22:13:00 | POST 开始 | SEL（E-2） |
| 22:14:55 | 引导交接，内核 t=0 ≈ 22:15:00 | 操作日志看门狗里程碑（E-3） |
| 22:15–23:34 | 122 核（maxcpus=122）稳定运行 80 分钟 | 黑匣子无异常 |
| 23:34:44 | 运维人员热插拔上线 CPU122（t=4784.3s；经主机 OS 侧发起——该时刻 KVM 会话处于超时断开状态 23:16:54–23:39:25） | E-3/E-5 |
| +17ms | 调度域重建 WARN（`kernel/sched/topology.c:1021`，cpuhp/122） | E-5 |
| +27.08s | 致命崩溃：读保存的寄存器报"地址无映射"（23:35:11；即 §3.2 的故事，机制见 §4.2） | E-5 |

### 6.4 kdump 缺失与证据缺口

崩溃内核获得约 12 分钟，未完成 vmcore 落盘即被看门狗中止；`/var/crash` 为空（10-10 已核实）。后果：**解释 A/B 之别（§4.2）与位点 ①/② 之别（§5.3）的判据缺失**——这是本报告两处停在强推/假设级的唯一原因。

### 6.5 存活的启动怎么解释

10-04 07:32 启动存活 5 天、若干 122 核启动存活数小时——差异仅在"CPU122 是否进入运行集合"（§3.4）。固件摘核（9-17）为**易失状态**：9-22–24、9-29–30 仍有崩溃簇，10-02 冷上电后坏核完全回归。摘核态的精确保持边界不可观测（黑匣子缓冲不覆盖），列为未决（§9）。

## §8 处置与建议

### 8.1 立即（当前已生效，需固化）

CPU122 离线（127 核运行）。**持久化**：udev 规则或 systemd oneshot 在每次启动时 `echo 0 > /sys/devices/system/cpu/cpu122/online`。验证：重启后 `cat /sys/devices/system/cpu/online` 为 `0-121,123-127`，且 `dmesg` 无 cpu122 上线记录。

### 8.2 备选持久方案

| 方案 | 优点 | 代价 |
|---|---|---|
| BIOS 核禁用（若 J353 BIOS 提供 Active Processor Cores） | 不依赖 OS | 需确认 BIOS 能力 |
| `nr_cpus=122` | 内核级硬上限，热插拔无法越过 | 同时屏蔽健康的 CPU123 |

### 8.3 送厂 FA 检查清单（按 §5.3 排序）

1. 私有 L2 的 MSHR/在途请求关联逻辑（响应数据写回选择的 CAM/比较器）；
2. L1 tag 阵列与 way 选择逻辑、页表遍行读通路；
3. LSU store buffer 转发 CAM（并存可能）。

随附：本报告 + `evidence-20261009/`（E-1～E-8，含五次崩溃原始控制台与反汇编）+ 9 月前置报告。

### 8.4 kdump 可用性修复

下次复发前必须解决与 SBSA 看门狗的冲突：经 BMC 延长或禁用该看门狗，或压缩转储策略使落盘在超时窗口内完成。否则该机永远取不到 vmcore，R3/R4 停留在强推/假设级（§6.4）。

### 8.5 可观测性

内核 cmdline 加回 `console=ttyS0,115200`（当前 `console=tty0` 使 SOL 串口无输出；BMC 黑匣子不受影响）。
