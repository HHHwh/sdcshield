## 0. 结论摘要(先给结论)

**物理核 MPIDR `0x0900060200`(节点 0x09、cluster 0x06、core 2;正常启动时的逻辑 CPU122)是一个微架构层面的"水银核心"(mercurial core),其核内数据通路存在"有效数据错行替换"缺陷,导致该机器在单次加电会话中连续 3 次启动均在 19~34 秒内崩溃,而固件在第 4 次启动时将该物理核从启动集合中摘除(127 CPU 启动)后,系统干净启动至登录界面。**

核心证据链(全部可溯源到日志行号,见附录 A):

1. **单变量 A/B 实验(现场天然完成,实验室都很难设计出来):**
   - Boot 1(128 CPU):18.947s,**CPU122** 内核栈溢出 panic(寄存器含 SWAR 字符串处理常量 + 模块名 ASCII + 指令编码);
   - Boot 2(128 CPU):33.561s,**T1903 PC 对齐异常(ESR 0x8a000000,EC=0x22)** 引爆 36 次 "Unable to handle kernel paging request" 群崩(28+ 线程在 1.2ms 内、跨 20+ 个 CPU),页表被零化/覆写;
   - Boot 3(128 CPU):33.493s,**CPU122** 在 `find_busiest_group+0x98` 双重故障 panic(页表项损坏 + 寄存器组被替换为 printk 缓冲区文本与 NOP 指令编码);
   - Boot 4/**Boot D(127 CPU)**:`0x0900060200` 从二级启动序列中**消失**(逻辑编号整体前移,CPU122 改由 `0x0900060300` 占据)——同一 BIOS、同一内存、同一 LLC/互连/GIC,唯一被移除的变量就是这个物理核,**启动干净,存活至 SOL 正常关闭**。

2. **"有效数据错行替换"签名(不是随机位翻转):** 损坏值的内容全部是**当时本应流经该核数据通路的其他合法数据**——printk 日志文本、格式化字符串(`"%d,"`、`"rgs=%p\n"`)、驱动/模块名 ASCII(`"MD_devic"`、`"atch_ISA"`)、ARM64 指令编码(`d503201f`=NOP、`d65f03c0`=RET、`f940xxxx`=LDR)、SWAR 字符串内核常量(`01010101`/`7f7f7f7f`/`fefefeff`/`80808080`)、零填充页。**被替换的数据本身都是合法码字 → SECDED/ECC 完全无感 → RAS 全静默**(BMC 侧 `CorrectErrorThreshold=1770 / CorrectErrorStorm=0`,内核侧 ghes_edac 已注册但零错误记录)——这正是 docs/cpu §10.7.6 "RAS 全静默 + 持续崩溃 = 通路故障强信号" 的铁证模式。

3. **微架构根因层级:** 缺陷位于 0x0900060200 核内(或其私有 L1D/L2)的**装入返回通路 / 存储提交(写回)通路的行标识(line identity)故障**——读侧把"别的行的合法内容"送进寄存器组(Boot 1/3 的寄存器剖析直接捕获),写侧把"本核正在写入的行内容"落到错误的物理行上(页表页被零化/被代码字节覆写 → Boot 2 全系统群崩)。按 docs/cpu §10.7.5 的现场形态分类,属于 **D1/D2 通路类"错源/错行替换"族**;按 §10.9.2 权重表,本案例命中三条高权异常(嵌套故障、DABT SP-relative 20.77x、Undef/PC 类 17.80x)。

4. **置信度评估(§10.9.3 七步法):** P1 单核浓度(3/3 次失败启动的直接肇事/首错核,另 `boot panic.txt` 再证 2 次 CPU122 崩溃;若故障在 128 核均匀分布,同核 5 连发的零假设概率 < 10⁻⁸)+ P2 重启复发(3/3)+ P3 RAS 静默(全静默)+ P5 异常加权(高权三连)→ **高置信:水银核心,立即隔离(平台已自动完成)+ 送厂 FA**。

## 3. Boot 1 取证:CPU122 栈溢出——存储了"别人的数据"的寄存器组

**事件(行 5129-5170):** CPU122 执行 `module_patient_check_exists`(LR 行 5139)时,SP 已跌落到任务栈底以下(`sp = 0xffff80008cd500a0`,任务栈 `[0xffff80008cd58000..0xffff80008cd5c000]`,SP 低于栈底 **0x7F60 字节**);异常压栈对 `[SP]` 的写访问触发 DABT——**ESR 0x96000047 = EC 0x25(当前 EL 数据中止)、IL=1、ISS bit6=1(WnR=1,写)、FSC=0x07(L3 翻译故障)**,FAR=SP。内核检测到 SP 越界,走 `__bad_stack → panic_bad_stack → nmi_panic("kernel stack overflow")`。

**寄存器组剖析(行 5141-5150)——本案第一份"替换内容"样本:**

| 寄存器 | 值 | 小端解码 | 内容类别 |
|---|---|---|---|
| x8 | `0101010101010101` | — | SWAR 字节统计常量 |
| x7 | `7f7f7f7f7f7f7f7f` | — | SWAR ASCII 掩码 |
| x6 | `fefefeff64625e65` | `e^bd` + `fefefeff` | SWAR haszero 掩码 + ASCII |
| x5 | `8080808000000000` | — | SWAR 高位测试掩码 |
| x15 | `6c656e72656b0065` | `e\0kern\0`…("…e kernel") | 模块名文本 |
| x14 | `6c6261745f656369` | `ice_tbal` | 驱动/模块名文本 |
| x13 | `63697665645f444d` | `MD_devic` | 同上 |
| x12 | `4953415f68637461` | `atch_ISA` | 同上 |
| x11 | `00797375625f7478` | `xt_busy` | 同上 |
| x10 | `65746e6f635f646d` | `md_conte` | 同上 |
| x17 | `9400000091000000` | `BL #0` + `ADD X0,X0,#0` | **ARM64 指令编码** |
| x16 | `90000000d65f03c0` | `d65f03c0` = **RET** | **ARM64 指令编码** |

解读的三个层次:

1. **自洽的一半:** x5-x8 的 SWAR 常量组 + x10-x15 的模块名 ASCII,恰好是 `module_patient_check_exists`(模块名字符串比对,内核 strcmp/strlen 用 SWAR 实现)的**合法执行状态**——这段寄存器内容与 LR 指向的函数在语义上是配套的。
2. **不合法的一半:** x16/x17 里出现 **RET、BL 等指令编码**。通用寄存器组里出现指令流的字节,只有两类来源:(a) 模块映像 memcpy(模块 `.text` 通过 LSU 数据通路拷入,崩溃窗口恰在模块装载风暴)——那是**数据通路上正在流动的别的行**;(b) 取指通路与数据通路的串扰。无论哪种,都证明**该核的数据通路把"别的地址的合法内容"送进了指针类寄存器**。
3. **SP 失控的机理:** SWAR 字符串循环的迭代变量/帧链一旦被替换为垃圾(或其读入的栈帧内容被替换),epilogue 的出栈序列就会把垃圾弹入 SP,SP 一路跌破栈底,直到压栈写入命中栈底守护页 → 0x96000047(WnR=1)→ `__bad_stack`。这正是 docs/cpu §10.9.2 权重表里 **"DABT SP-relative 20.77x"** 的现场形态:SP 是内核最热数据依赖链,通路故障在它身上暴露得最快。

## 4. Boot 2 取证:36 事件群崩普查——一次"共享态投毒"的消费级联

### 4.1 事件时间结构与发起者

- **33.560890**(行 10431)T1903 第一个异常:`ESR 0x8a000000` → **EC=0x22 PC 对齐故障、IL=1**——PC 本身是垃圾(后续 dump 证实 `pc : 0x61000a5d73255b`,非 4 字节对齐,`Code: ????????` 完全不可读,pstate 亦异常)。其寄存器组(行 10896-10930)一半是合法内核指针(`ffffa1cd7xxxxxxx` slab/vmalloc 邻域),另一半是字符串碎片:`"data_loc"`(x24)、`"apter_nr"`(x19,adapter_nr)、`"_msgs__"`(x21)、`"sa16…ms"`(x22)、`"if"`(x26)、`"data/+wa"`(x8)。
- **33.561117 起 1.2ms 内**(行 10450-10769):28+ 线程在 **20+ 个不同 CPU** 上同时 "Unable to handle kernel paging request",故障地址绝大多数是**垃圾**(ASCII/指令编码,见 4.3);
- **33.563~34.962s**:余波 8 次(含 C45/C43 在异常上下文中的复发、T666 最后一次);
- **34.967797**(行 10940)`panic: SP/PC alignment exception` 收尾;`failed to stop secondary CPUs 2,10,…,116-123`(行 10952)——**122 在卡死名单内**。

**关键推理——"发起者 CPU 2"不能按字面采信,而且这不影响归因:** T1903 的 dump 是在自身寄存器/内存读取已腐烂的状态下打印的(PC 为垃圾、调用栈为垃圾、Code 全问号),"CPU: 2" 本身来自一次可疑的内存读取。更重要的是:**群崩的模式不是"多核同时自发损坏",而是"多核同时消费被投毒的共享态"**——各受害线程的故障地址互不相同(排除单一共享 VA 的页表故障),但**内容同源**(全是字符串/代码字节,即被投毒单元里覆写进去的东西)。这符合"投毒在先(秒级窗口内由肇事核的错行写回静默完成),消费在后(谁先碰到谁先死,首受害者落在哪个核是随机的)"模型。Boots 1/3 中肇事核自己先踩雷(寄存器/栈本地损坏先显性化),Boot 2 中投毒先于本地显性化完成——同一缺陷的两种显性化顺序。

### 4.4 页表被投毒的直接证据

```
                   pud=1000082fffffe403, pmd=1000082fffffd403, pte=0000000000000000
```
四级描述符"看起来合法"(bit0=1 valid、bit1=1 table、AF 位在),但指向的下一级物理地址是 `0x1000082ffffff000` 一类的**系统物理地址空间之外的值**,且 pud→pmd 的输出地址恰好逐级递减 0x1000——这不是任何真实分配器的行为模式,而是**页表内存被非页表内容覆写后"碰巧保留了描述符位型"**;遍历最终落在 pte=0 上,以 FSC=0x07(L3)失败。**页表 = 最高杠杆的投毒目标:一行页表被覆写,所有触及其覆盖 VA 的线程同时倒下——这是 1.2ms 内 28+ 线程群崩的最优解释。**

**T2169/CPU120(putname,行 10433-10476)——投毒内容的直接采样:** `fs/namei.c:264` WARNING(putname 检测到 filename 对象损坏)→ 随后 DABT,故障地址 `002c6425206563e9` 内容为 `"%d,"` 格式串碎片;其寄存器 x12/x13 = `=%ulu, ua` / `rgs=%p\n`(行 10446)——**printk 格式串**。CPU120 是 CPU122 的同 cluster 兄弟,消费了被投毒的 filename/slab 对象。

## 6. 微架构根因综合

### 6.1 缺陷签名:有效数据错行替换(ECC 盲区内的通路 SDC)

全部 40+ 份损坏样本(Boots 1-3 的寄存器组、故障地址、页表描述符)有一个共同结构:**被替换进来的值永远是"当时合法存在于缓存层次中的别的行"**——printk 文本、格式串、模块名、模块 `.text` 字节(装载风暴正当时)、SWAR 常量(内核 strcmp/strcpy 热路径)、零页。没有一份样本呈现"随机位翻转"(0→1/1→0 无模式位谱)或"固定粘滞位"。按 docs/cpu §10.7.5 的四族现场形态分类,这是 **"同类/异值替换"族(错源转发 + 错行替换,D1/D2 通路类)**,对应 formal 地图中 **LSQ 错源转发(37.6% SDC)与 AGU/fill 通路(100% DUE)两类高危害通路**;位谱指纹(§10.10 位谱指纹库)在本案表现为"整 32-bit 粒度内容替换",与 m1(同类指针替换)/m2(零塌缩)向量攻击的形态吻合。

**为何 RAS 全静默(§10.7.6 的教科书式复现):** SECDED/ECC 保护的是"存储单元内码字的位完整性"。当故障形态是"把 A 行的合法码字搬到 B 行的槽位"时,B 槽位上的码字**本身就是合法的**——ECC 校验必然通过。ghes_edac 无记录、BMC CorrectError 计数为零,不是 RAS 配置漏报,而是**这类缺陷在原理上不可被行内 ECC 检出**。这反过来把根因锁定在"行寻址/行标识/转发源选择"层——即 L1D 的 tag 比较/way 选择、LSU 的转发 CAM 匹配、fill 与写回的行标识——而非存储阵列本身。

### 6.2 传播链(一个缺陷站点,两种显性化)

```
缺陷站点:物理核 0x0900060200 的 L1D/LSU/私有L2 行标识通路(读侧 fill→PRF、写侧 store→writeback)
   │
   ├─ 读侧:装入返回"别的行"的合法内容 → 指针/迭代变量/返回地址被替换
   │     ├─ Boot 1:SWAR 模块名比对循环的帧链/迭代变量损坏 → SP 失控跌破栈底 → 栈溢出 panic(本地显性化)
   │     └─ Boot 3:find_busiest_group 的操作数被替换为 NOP 编码 + pt_regs 被替换为日志文本
   │            → 双重故障 panic(本地显性化,同窗口页表也已损坏)
   │
   └─ 写侧:本核正在写的行(模块代码、printk 缓冲、零页)落到错误物理行
         ├─ 页表页被零化/覆写(T2069 pgd=0、T2246 描述符链腐烂、合法 VA 翻译失败)
         ├─ 共享 slab/链表/函数指针被覆写为字符串与代码字节
         │     → Boot 2:任意核消费即倒 —— PC 对齐(T1903,函数指针/返回地址被替换)、
         │       28+ 线程 1.2ms 群崩(地址内容=投毒物)、IABT 跳入代码字节(两核同址)
         └─ 投毒先于肇事核本地显性化 → 首受害者落在其他核("CPU: 2"),随后全网级联
```

### 6.3 备择假设排除

| 备择假设 | 排除依据 |
|---|---|
| **内核软件 bug** | 三次崩溃首错点完全不同(模块名比对栈失控 / 调度域遍历双故障 / 系统级群崩);同一内核同一配置在摘除一个物理核后(Boot D)干净启动。软件确定性不依赖于某个物理核的在位与否。 |
| **DDR/DIMM 缺陷(系统级)** | Boot D 保留全部 DIMM/DDR 控制器/LLC/互连,仅摘除一个核,即干净。若 DDR 有缺陷,Boot D 必然复发。 |
| **LLC(HHA)/片间互连缺陷** | 同上——共享层在 Boot D 中原样在位。且若共享层故障,首错核应均匀分布,不会 5 次独立捕获(3 次启动 + boot panic.txt 2 次)全部锚定 `0x0900060200`。 |
| **ECC 可见的 DRAM 位翻转** | 零 RAS 记录 + 损坏内容全部为"合法别的行内容"(§6.1),与位翻转的随机位谱形态学矛盾。 |
| **频率/电压/环境瞬态** | 三次崩溃时刻不同(18.9s/33.5s/33.5s)、负载形态各异;boot panic.txt 跨会话同核复发;Boot D 同环境干净。瞬态不能解释"摘一个核就好"。 |
| **"CPU: 2" 字面采信 → Boot 2 首错在 CPU2** | 该 dump 自身深度腐烂(pc=垃圾、Code 全 ?、调用栈垃圾);且群崩形态是"消费级联"而非"多点自发故障"(§4.1)——首受害者核的位置不影响"投毒源唯一"的判定。 |

### 6.4 七步法置信度(docs/cpu §10.9.3)

| 步 | 判据 | 本案 |
|---|---|---|
| P1 单核浓度 | 1 周内单核异常占比 >60% | **5/5 次崩溃肇事/首错锚定 0x0900060200**(均匀零假设 p < (1/128)⁴ ≈ 3.7×10⁻⁹,已计入 Boot 2 首错位置不可信) |

## 7. 芯片设计优化建议

以下建议遵循 docs/cpu §10.10 的设计哲学:**不保护"值的正确性"(那需要知道正确值),而保护"路径的完整性"(值没有被在途中换掉)**;每条建议对应本案一个被实证的损坏形态,并给出验证路径。先给结论表:

| # | 建议 | 对应现场形态 | 对应 docs/cpu 依据 | 校验类型 |
|---|---|---|---|---|
| 1 | AGU→MMU 地址形状预检 | 34/36 个垃圾故障地址 + CPU122 的垃圾 PC | §10.10 建议 1(AGU 合法性校验) | 形状不变量 |
| 2 | fill→PRF / store→writeback 行标识端到端校验 | Boot 3 寄存器被替换为日志文本/NOP 编码;页表被零化 | §10.10 建议 3(check-after-path)泛化 | 端到端一致 |
| 3 | LSU 转发源 age-ID 冗余比较 | SWAR 常量/模块名进入指针寄存器(错源转发族) | §10.10 建议 2(age-ID 校验) | 来源不变量 |
| 4 | 页表通路的描述符合法性校验 + PTE 写限定 | T2069 pgd=0、T2246 腐烂描述符链、合法 VA 翻译失败 | §10.7.5 D3 通路;页表 = 最高杠杆投毒目标 | 域约束 |
| 5 | RAS:把"错行替换"变成可报告错误 + 修复风暴升级策略 | RAS 全静默 + CorrectErrorStorm=0 | §10.7.6(静默盲区) | 可观测性 |
| 6 | 固件级核健康自治摘除 | Boot D 人工/自动摘核即愈 | §10.9.4(水银核心隔离)产品化 | 容错 |

**1) AGU→MMU 地址形状预检(成本最低、收益立现)。** 本案 34/36 个故障地址违反**规范地址形状**:48-bit VA 配置下 bits[63:48] 必须全 0 或全 1,而 `72e8706c…`、`002c6425…`(ASCII)、`d503201f…`(指令编码)全部非法;CPU122 的 `pc=0x61000a5d73255b` 同样非规范且不对齐。形状约束是**上下文固定的静态约束**(TCR 的 T0SZ/T1SZ + 对齐),比较器规模有界——远比通用 ECC 便宜。校验点放在 AGU 输出送 MMU 之前(以及 PC 生成送取指之前):非法形状地址在触发昂贵的翻译故障/取指冒险**之前**被拦截,并**按核计数上报 RAS**。本案若配备此校验,静默 SDC 在 Boot 1 第一次错行替换时就会变成一条按核累计的遥测记录——P1 铁律无需等到 5 次崩溃才触发。

**2) 行标识(line-identity)端到端校验——fill 与写回两段都做。** 本案的原理性盲区是 SECDED 无法检出"合法码字换行"。闭合方法:让**行标识随数据同行**——fill 数据从 L2/LLC 进入 L1D 时携带其 PA tag 的冗余副本(或全行 CRC 的 tag 绑定版本),在 **PRF 写口**再校验一次(§10.10 建议 3 的 fill→PRF 段);store buffer/写回通路在提交时冗余比较"行槽 tag 与请求 PA"。任何一段 tag 与数据不匹配,即以新的错误记录类别(implementation-defined error,经 GHES 上报)报告为 **"line substitution detected"**。该检不出"值算错了"(ALU 类 SDC),但精确覆盖本案的"值被换掉了"——错源/错行族。

**3) LSU 转发源 age-ID 冗余比较。** Boot 1 的寄存器组(SWAR 常量 + 模块名 + 指令编码)是**错源转发**的典型现场:load 从 store 队列/LSQ 拿到了**别的 store 的数据**——模块装载风暴中 store 队列里满是代码字节与字符串,正是被转发进指针寄存器的内容谱。formal 地图中错源转发 37.6% SDC(§10.10 表);对策是转发命中后附带比较"被选中 store 的 age-ID 与地址匹配计算结果"(冗余编码 age 字段),对合法域替换类故障单奇偶无效、需双份冗余比较。

**4) 页表通路两级防护。** 页表是本案最高杠杆目标(1 行投毒 → 28 线程 1.2ms 崩溃)。两级:(a) **遍历侧**——MMU 页表遍历器对描述符输出 PA 做"系统物理内存窗口"合法性检查(本案 T2246 的 `0x1000082ffffff403` 指向物理地址空间之外的荒谬 PA,在遍历时即可拦截并作为 RAS 事件上报,而不是让遍历一路走到底变成 L3 fault);(b) **写入侧**——PTE 修改只来自内核 `set_pte` 族的狭窄指令集合,可为"最近被写 PTE 行"维护一个小型带 ECC 影子锁阵列,写回时校验"该行确实是被授权的 PTE 写请求命中",拦截错行写回落到页表行上的通路故障。

**5) RAS 可观测性:新检出的错误类别必须配升级策略。** 本案 BMC `CorrectErrorStorm=0`、阈值 1770/6000,意味着即使 1-2 的新检测器产生了计数,在现有策略下也不会升级、不会告警。设计要求:(a) 任何新错误类别(line substitution、address-shape violation)在 ERST/GHES 中**一票即报**(它们不是概率性噪声,每次发生都是通路故障的直接证据);(b) 风暴判定与阈值策略必须与"检出的语义"挂钩,而不是统一 6000 次的惰性默认——把 §10.7.6 的"RAS 静默盲区"从"发现不了"变成"发现了必定吵醒人"。

**6) 固件级核健康自治摘除(把 Boot D 从偶发变成机制)。** 本案的最终救赎是平台在第 4 次启动把 0x0900060200 摘掉了——但这依赖三次完整崩溃的代价。产品化:CPU 按核维护"首错计数/地址形状违规计数"并跨复位持久化到 BMC;阈值触发(BMC/固件在下次复位时)自动去配置该核、降级启动(128→127 核),并自动开 FRACAS 工单 + 点亮 FRU 告警灯。配套:**摘核是观测的延续而不是终点**——被摘核保留最小化的诊断负载通道(DFT 向量/位谱采样),持续采集故障核行为数据供 FA 前的根因细化(§10.9.4 的分级隔离哲学)。

**7) DFT 向量包扩充(§10.10 方法论的直接延伸)。** 按现场形态反推测试向量,在产线筛除同类次品:

| 向量 | 攻击形态 | 对应本案现场 |
|---|---|---|
| v-sub | L1D/L2 way 选择冲突(march 式地址对制造 tag 碰撞) | 错行替换族(全部样本) |
| v-spar | SWAR 字符串内核(0x7f/0xfe/0x80/0x01 常量)+ 紧随的指针解引用链,比对指针校验和 | Boot 1 寄存器组签名 |
| v-pte | 页表页邻域的 store 风暴 + 随后的全区间页表遍历校验 | Boot 2 页表投毒(T2069/T2246) |

按 §10.10 的"形态学→测试学"闭环要求,向量必须在故障次品上复现签名(4/4 实证标准)后方可入产线包;位谱指纹库相应增加"32-bit 粒度整词替换"指纹,使未来现场案例可以"验指纹定根因"。

## 8. 运维处置建议(立即执行)

1. **维持 0x0900060200 的去配置状态**(不要在未 FA 前恢复 128 核启动);确认固件摘核的持久性(跨整机断电)。
2. **按"水银核心"流程隔离 + 送 FA:** 该 die/socket 返厂,向 FA 提供:五次崩溃的完整 SOL 日志、MPIDR 级首错归因表(附录 A)、Boot D 摘核对照结论。FA 重点关注该核的 L1D tag 阵列/way 选择逻辑、LSU 转发 CAM、私有 L2 写回通路。
3. **fleet 级预防:** 把"启动窗口首错核遥测"(MPIDR 级)纳入 fleet 监控,P1 铁律(单核占比 >60%)扩展覆盖**早期启动崩溃**——水银核心的最廉价暴露窗口就是开机前 60 秒;同批次 J353 G3(BC83AMDA01-7270Z)按此指标筛查。
4. **邻居核观察:** 同 cluster 的 `0x0900060000/0100/0300`(逻辑 120/121/123)在 Boot 2 中仅作为受害者出现(CPU120 putname),但共享电源/时钟域,FA 结论出来前列入重点观察名单。
5. **RAS 配置复核:** 与厂商确认 CorrectErrorStorm=0 与 6000 阈值的出厂语义;在固件支持 §7.5 的新错误类别前,任何 ghes_edac/CPMU 计数都只能作为下限理解。
